# Database and Authentication Migration PRD

**Version**: 1.0
**Author**: Gnosis Team
**Date**: 2026-02-01
**Status**: Draft
**Spec Type**: New feature (migration of existing feature set)
**Spec Depth**: Detailed specifications
**Description**: Migrate Gnosis away from Supabase and adopt Clerk for authentication and Prisma + PostgreSQL (Vercel Postgres) for the database, replicating the proven stack from the Syntra project.

---

## 1. Executive Summary

This spec defines the migration of Gnosis from Supabase (auth + database) to Clerk (auth) + Prisma/PostgreSQL (database). Supabase has caused friction with OAuth setup, migrations, and local development. The target stack is battle-tested in the Syntra project and will simplify auth (dashboard-configured Google OAuth, built-in UI components) and database operations (type-safe Prisma ORM, `db:push` workflow). This is a clean infrastructure swap with no feature additions or removals.

## 2. Problem Statement

### 2.1 The Problem
Supabase is causing development friction for the Gnosis project across three areas: OAuth configuration requires manual code for Google sign-in callbacks, database migrations use raw SQL with no type safety, and local development requires running the full Supabase stack. The developer wants a unified stack across projects (Gnosis and Syntra) to reduce context-switching and maintenance burden.

### 2.2 Current State
Gnosis currently uses:
- **Supabase Auth** with manual Google OAuth implementation (callback route, cookie management, custom sign-in/sign-up server actions)
- **Supabase PostgreSQL** with raw SQL migrations, manually defined TypeScript types (`src/types/database.ts` - 185 lines), and Supabase client queries throughout the data layer
- **Supabase SSR** package for cookie-based session management in middleware

This requires 6 Supabase-specific files, manual type definitions mirroring the SQL schema, and RLS policies for data access control.

### 2.3 Impact Analysis
- **Developer productivity**: Every database schema change requires updating both SQL migrations and TypeScript types manually
- **OAuth maintenance**: Custom OAuth callback route and cookie management code is boilerplate that Clerk eliminates entirely
- **Cross-project consistency**: Syntra and Gnosis use different stacks, doubling the surface area for infrastructure knowledge
- **Local development**: Supabase local dev requires Docker and the Supabase CLI, adding setup friction

### 2.4 Business Value
- **Reduced maintenance**: Clerk handles auth UI, OAuth, and session management out of the box
- **Type safety**: Prisma generates TypeScript types from the schema, eliminating manual type definitions
- **Unified stack**: Same patterns across Gnosis and Syntra means faster development and fewer bugs
- **Simpler deployment**: Vercel Postgres + Clerk are both Vercel-native, simplifying the deployment pipeline

## 6. Non-Functional Requirements

### 6.1 Performance
- Database queries via Prisma should have comparable or better performance to the current Supabase client queries
- Clerk middleware should add minimal latency to route resolution (Clerk SDK is optimized for edge runtime)
- Connection pooling via Vercel Postgres pooled URL must be used for all Prisma queries in production

### 6.2 Security
- Clerk handles all authentication security (password hashing, OAuth token management, session tokens, CSRF protection)
- Row-level data access is enforced at the application layer (all queries filter by `userId` from the authenticated Clerk session) -- replaces Supabase RLS policies
- The Clerk secret key (`CLERK_SECRET_KEY`) must never be exposed to the client
- Database connection strings must be kept server-side only

### 6.3 Scalability
- Vercel Postgres with connection pooling supports the expected load (single developer, small user base for now)
- Prisma's query engine handles connection management efficiently in serverless environments

### 6.4 Accessibility
- No changes to accessibility -- the migration is infrastructure-only
- Clerk's `<SignIn />` and `<SignUp />` components meet WCAG 2.1 AA standards by default

## 7. Technical Considerations

### 7.1 Architecture Overview
The migration replaces two infrastructure layers while keeping the application architecture (Next.js App Router with server components, server actions, and API routes) unchanged:

1. **Auth layer**: Supabase Auth (custom implementation) → Clerk (managed service with built-in components)
2. **Database layer**: Supabase PostgreSQL (raw queries via Supabase client) → Vercel Postgres (Prisma ORM queries)

The server actions pattern is preserved. No tRPC adoption.

### 7.2 Tech Stack
- **Frontend**: Next.js 16.1.6, React 19.2.3, Tailwind CSS 4 (unchanged)
- **Auth**: Clerk (`@clerk/nextjs` ~6.x)
- **Database**: PostgreSQL via Vercel Postgres
- **ORM**: Prisma (`@prisma/client` ~5.x, `prisma` ~5.x)
- **AI**: Groq SDK (unchanged)
- **Testing**: Vitest (unchanged)

### 7.3 Integration Points

| System | Integration Type | Purpose |
|--------|-----------------|---------|
| Clerk | SDK + Dashboard | User authentication, OAuth, session management, user profile (display name, avatar) |
| Vercel Postgres | Database URL | PostgreSQL database hosting with pooled connections |
| Prisma | ORM | Type-safe database queries, schema management, migrations |
| Groq API | REST API | AI chat completions (unchanged) |

### 7.4 Technical Constraints
- Must use Next.js App Router patterns (no Pages Router)
- Must maintain server actions for mutations (no tRPC)
- Clerk free tier limits apply (10,000 MAU)
- Vercel Postgres has connection limits on free/hobby plans (use pooled connections)
- Prisma `db push` for schema sync (no migration files in dev, matching Syntra pattern)

### 7.6 Prisma Schema

```prisma
generator client {
  provider = "prisma-client-js"
}

datasource db {
  provider  = "postgresql"
  url       = env("DATABASE_URL")
  directUrl = env("POSTGRES_URL_NON_POOLING")
}

model User {
  id               String   @id @default(cuid())
  clerkId          String   @unique
  email            String   @unique
  currentChapterId String?
  createdAt        DateTime @default(now())
  updatedAt        DateTime @updatedAt

  progress       UserProgress[]
  messages       ConversationMessage[]
  currentChapter Chapter?              @relation(fields: [currentChapterId], references: [id])

  @@index([clerkId])
}

model Chapter {
  id               String   @id @default(cuid())
  chapterNumber    Int      @unique
  title            String
  description      String
  targetVocabulary Json     @default("[]")
  targetGrammar    Json     @default("[]")
  createdAt        DateTime @default(now())

  scenarios Scenario[]
  users     User[]

  @@index([chapterNumber])
}

model Scenario {
  id                 String   @id @default(cuid())
  chapterId          String
  scenarioNumber     Int
  title              String
  contextDescription String   @db.Text
  agentRole          String   @db.Text
  targetPhrases      Json     @default("[]")
  systemPrompt       String   @db.Text
  createdAt          DateTime @default(now())

  chapter  Chapter              @relation(fields: [chapterId], references: [id], onDelete: Cascade)
  progress UserProgress[]
  messages ConversationMessage[]

  @@unique([chapterId, scenarioNumber])
  @@index([chapterId, scenarioNumber])
}

model UserProgress {
  id             String    @id @default(cuid())
  userId         String
  scenarioId     String
  completed      Boolean   @default(false)
  accuracyScore  Float?
  vocabularyUsed Json?
  completedAt    DateTime?
  createdAt      DateTime  @default(now())

  user     User     @relation(fields: [userId], references: [id], onDelete: Cascade)
  scenario Scenario @relation(fields: [scenarioId], references: [id], onDelete: Cascade)

  @@unique([userId, scenarioId])
  @@index([userId])
  @@index([scenarioId])
}

model ConversationMessage {
  id          String   @id @default(cuid())
  userId      String
  scenarioId  String
  role        String
  content     String   @db.Text
  corrections Json?
  createdAt   DateTime @default(now())

  user     User     @relation(fields: [userId], references: [id], onDelete: Cascade)
  scenario Scenario @relation(fields: [scenarioId], references: [id], onDelete: Cascade)

  @@index([userId, scenarioId, createdAt])
}
```

## 8. Scope Definition

### 8.1 In Scope
- Remove all Supabase packages and Supabase-specific code
- Install and configure Clerk for authentication
- Install and configure Prisma with Vercel Postgres
- Create Prisma schema matching all current Gnosis tables
- Migrate all Supabase queries to Prisma queries
- Replace auth pages with Clerk components
- Replace middleware with Clerk middleware
- Convert seed data to Prisma seed script
- Update environment variables
- Update `src/lib/env.ts` for new variable validation

### 8.2 Out of Scope
- **User data migration**: No migration of existing Supabase user accounts or progress data. Users will need to re-register via Clerk.
- **tRPC adoption**: Gnosis continues using server actions; no tRPC integration.
- **New features**: No new pages, components, or capabilities added.
- **Clerk webhooks**: Not implementing webhook-based user sync. Using on-demand `getOrCreateUser` pattern instead.
- **Supabase storage**: Gnosis does not use Supabase Storage, so no file migration needed.
- **Visual redesign**: Auth pages will use Clerk's components with minimal styling adjustments.

### 8.3 Future Considerations
- Clerk webhooks for real-time user sync (if needed for admin features)
- Prisma migration files for production schema versioning (currently using `db:push`)

### 14.1 Glossary

| Term | Definition |
|------|------------|
| Clerk | Managed authentication service providing sign-in/sign-up UI, OAuth, and session management |
| Prisma | TypeScript ORM that generates type-safe database client from a schema file |
| Vercel Postgres | Managed PostgreSQL database service integrated with Vercel deployments |
| RLS | Row-Level Security -- Supabase feature for database-level access control (being replaced by application-level checks) |
| `db:push` | Prisma command to sync schema to database without creating migration files |
| `clerkMiddleware` | Clerk's Next.js middleware for automatic session management and route protection |
| Server Actions | Next.js feature for server-side form handling and mutations |

### 14.2 Key Pattern: Getting the Authenticated User + DB Record

After migration, the pattern for getting the authenticated user in server components and API routes will be:

```typescript
import { auth, currentUser } from "@clerk/nextjs/server";
import { db } from "@/server/db";

// In a server component or API route:
const { userId: clerkId } = await auth();
if (!clerkId) redirect("/sign-in");

// Get or create the database user
const user = await db.user.upsert({
  where: { clerkId },
  update: {},
  create: {
    clerkId,
    email: (await currentUser())?.emailAddresses[0]?.emailAddress ?? "",
  },
});

// Now use user.id for all database queries
const progress = await db.userProgress.findMany({
  where: { userId: user.id },
});
```

### 14.3 Key Pattern: Prisma Singleton (src/server/db.ts)

```typescript
import { PrismaClient } from "@prisma/client";

const globalForPrisma = globalThis as unknown as {
  prisma: PrismaClient | undefined;
};

export const db = globalForPrisma.prisma ?? new PrismaClient();

if (process.env.NODE_ENV !== "production") {
  globalForPrisma.prisma = db;
}
```

### 14.4 Key Pattern: Clerk Middleware (src/middleware.ts)

```typescript
import { clerkMiddleware, createRouteMatcher } from "@clerk/nextjs/server";

const isProtectedRoute = createRouteMatcher([
  "/dashboard(.*)",
  "/chapters(.*)",
  "/progress(.*)",
  "/profile(.*)",
  "/api/chat(.*)",
  "/api/progress(.*)",
  "/api/conversations(.*)",
]);

export default clerkMiddleware(async (auth, req) => {
  if (isProtectedRoute(req)) {
    await auth.protect();
  }
});

export const config = {
  matcher: [
    "/((?!_next/static|_next/image|favicon.ico|.*\\.(?:svg|png|jpg|jpeg|gif|webp)$).*)",
  ],
};
```
